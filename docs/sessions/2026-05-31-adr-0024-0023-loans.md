## ADR-0024 — Odstránenie role TEAM_MANAGER ✅

`TEAM_MANAGER` bol mŕtvy pozostatok SFZ modelu bez vlastného oprávnenia; beneficiary
model (0023) nahradil dôvod jeho existencie. Odstránený z `UserRole` enumu aj kódu.
Výsledné roly: EMPLOYEE, ASSET_MANAGER, ADMIN, EXTERNAL.

Rozsah bol väčší než pôvodný odhad ADR — TypeScript po odstránení enum hodnoty odhalil
11 súborov so živým `TEAM_MANAGER` (nie len enum + 2 guardy + 1 test, ako ADR čakal):

- `packages/shared-types/src/enums/user-role.ts` — odstránená hodnota + akt. popisy rolí
- `canRead` guardy: `asset-conditions`, `asset-types`, `assets`, `categories`, `locations`,
  `organisations` (canReadOwn), `stock`, `loan-requests`, `loans` routes
- `invitations.routes.ts` — odstránený z `ROLE_LABELS` mapy
- `memberships.routes.ts` — odstránený z `PatchMembershipBodySchema` enumu
- Testy: `rbac.test.ts` (zmazaný `TEAM_MANAGER forbidden writes` blok), `users-list.test.ts`
  (fixture + RBAC `.each` tabuľka), `users-patch.test.ts` ("adds an additional role" → ASSET_MANAGER),
  `user.test.ts` v shared-types ("viac rolí naraz" → ASSET_MANAGER)
- Migrácia `2026-05-31-remove-team-manager-role.ts` — `$pull` z `memberships.roles` +
  `users.roles`, fallback `['EMPLOYEE']` ak by pole ostalo prázdne; zaregistrovaná v `runner.ts`

**POZN.:** `Membership.teams[].role: 'MANAGER'` (rola v rámci tímu) sa NEMENILA — iný koncept.

**Ešte overiť:** SFZ Asset-Management repo — či tam `TEAM_MANAGER` nemá živé použitie.

Commit: `feat(roles): odstránenie role TEAM_MANAGER z UserRole (ADR-0024) + migrácia`

## ADR-0023 — Žiadosť v mene inej osoby + priama výpožička ✅

Upravený model z ADR-0012 (kde platilo žiadateľ = vypožičiavajúci, Loan vždy zo žiadosti).

### Dve zmeny

1. **`LoanRequest.beneficiaryId`** — žiadosť pre seba alebo pre inú osobu.
   `requesterId` = kto podal, `beneficiaryId` = pre koho (default = requesterId).
   Pri approve `Loan.borrowerId = beneficiaryId`. Žiadať za hocikoho smú všetci (EMPLOYEE+) —
   gatekeeper je správca pri schvaľovaní. Read-RBAC: EMPLOYEE vidí `requesterId === self`
   ALEBO `beneficiaryId === self`. Beneficiár musí byť aktívny člen toho istého tenanta.
2. **Priamy Loan bez žiadosti** — `Loan.requestId` je nullable; nový `POST /v1/loans`
   (ASSET_MANAGER/ADMIN) vytvorí výpožičku priamo `AVAILABLE → BORROWED` (bez RESERVED).
   Pokrýva US-017 quick loan, ktorý #5 odložil.

### Vykonané zmeny

- `packages/shared-types/src/schemas/loan.ts` — `beneficiaryId` na `LoanRequestSchema`
  (voliteľný v `CreateLoanRequestSchema`), `requestId` nullable na `LoanSchema`,
  nový `CreateDirectLoanSchema`
- `audit-log.ts` — nová akcia `LOAN_CREATED_DIRECT`
- `loans.service.ts` — beneficiary validácia, `borrowerId = beneficiaryId` pri approve,
  nová `createDirectLoan` metóda, EMPLOYEE list filter cez requester+beneficiary,
  `assertCanReadLoanRequest` rozšírený o beneficiára
- `loan-requests.repository.ts` — `beneficiaryId` parameter v `list()` (self-view `$or`)
- `loan-requests.routes.ts` — body schema `beneficiaryId` + injektovaný `fastify.mongo.db`
- `loans.routes.ts` — nový `POST /v1/loans` endpoint (canWrite)
- Migrácia `2026-05-31b-loan-request-beneficiary.ts` — backfill `beneficiaryId = requesterId`
  na existujúcich žiadostiach; zaregistrovaná v `runner.ts`
- `tests/integration/loans-adr-0023.test.ts` — beneficiary + direct loan testy
- Fixtures `loan.test.ts` (shared-types) doplnené o `beneficiaryId`

Commit: `feat(loans): beneficiary model + priama výpožička (ADR-0023)`

- `chore(api): refresh openapi.json (ADR-0023 loan endpoints)`

## 🔑 Kľúčové zistenie — DB handle v service

Debugging integračných testov ADR-0023 (8 → 6 → 0 padajúcich) odhalil systematický bug:

> **`mongoClient.db()` BEZ argumentu vracia default DB z connection URI — NIE tenant/test DB.**

`fastify.mongo.db` je `client.db(MONGO_DB_NAME)` = správna DB (v testoch
`sfz_asset_management_test`). Ale service robil cross-collection lookupy (users, memberships)
cez `this.mongoClient.db()` bez mena → čítal zo zlej databázy → testy hlásili
`"user does not exist or is not active"` aj keď user existoval.

**Riešenie:** `LoansService` dostáva `fastify.mongo.db` ako nový (posledný, voliteľný)
konštruktor parameter; pridaný `getDb()` helper, ktorý ho preferuje pred `mongoClient.db()`.
Všetky `mongoClient.db()` výskyty v service (vrátane pôvodných fire-and-forget email metód,
ktoré mali ten istý latentný bug) prepísané na `getDb()`.

Toto je rovnaký typ multi-tenant bugu, aký mal kedysi `Loan` schema (chýbajúci
`organisationId`) a aký ADR-0022 plánuje opraviť na `LoanProtocolSchema`.

### Ďalšie drobné fixy počas debug slučky

- Service `findOne({ _id: id as never })` (string vs ObjectId) → `new ObjectId(id)`
- Testy posielali `beneficiary._id` (ObjectId) namiesto `String(...)` do API očakávajúceho hex string
- Membership check má fallback na legacy `user.organisationId === tenantId` (fixtures
  `provisionUser` nevytvárajú membership record)
- `users-patch` test: API vracia roly v inom poradí → `expect.arrayContaining`

## openapi.json refresh — pripomienka

CI guard (`openapi:export:offline -- --check`) spadol, lebo spec na disku bol stale
po zmene schém. Lokálny `openapi:export` (cez Atlas) zlyhal na **bad auth** —
credentials v `.env.local` neplatné. Riešenie: **offline variant** `openapi:export:offline`
(in-memory MongoMemoryServer, žiadny Atlas) regeneruje spec bez pripojenia.

> **Pripomienka:** Atlas auth v `.env.local` treba aktualizovať (rotované heslo alebo
> IP allowlist) — blokuje lokálny `pnpm dev` proti Atlasu. Neblokuje testy ani offline export.

Zvážiť: pridať `openapi:export:offline` do pre-commit hooku (lint-staged), aby sa spec
regeneroval automaticky a CI guard nikdy nezlyhal.
